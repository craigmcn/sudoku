# Sudoku

A browser-based Sudoku game built with TypeScript and Vite, deployed to Netlify. No runtime dependencies — pure vanilla TS.

## Architecture

The project is split into TypeScript modules plus static HTML/CSS:

- **[src/solver.ts](src/solver.ts)** — Core types and algorithms. Exports `Board` (9×9 grid of `number | null`), `isValid`, `solve` (backtracking solver), and `countSolutions` (stops early at `max`, restores the board on return).
- **[src/rng.ts](src/rng.ts)** — `mulberry32(seed)`, a small seedable PRNG returning a `Math.random`-compatible `() => number` in `[0, 1)`. Exists so puzzle generation can be made reproducible from a seed (daily puzzles, puzzle-ID hashing) without pulling in a larger dependency.
- **[src/puzzleId.ts](src/puzzleId.ts)** — `hashSolution(board)`, a stable content-hash ID for a solved grid (two 32-bit FNV-1a passes with different multipliers, concatenated as base36). Used to key puzzle documents so two independently-generated puzzles with the same solution collapse onto the same ID/stats instead of duplicating.
- **[src/generator.ts](src/generator.ts)** — Generates puzzles. Fills a board with a randomized backtracking fill, then removes cells one-by-one while verifying unique solution via `countSolutions`. Clue counts per difficulty: easy 46, normal 36, hard 28, expert 22 (may exceed target — `generatePuzzle` stops removing early if uniqueness would break). `generatePuzzle(difficulty, seed?)` — an optional numeric `seed` makes the whole generation (fill order and removal order) deterministic via `mulberry32`; omitting it falls back to `Math.random` as before. Benchmarks ~130ms for `'expert'`.
- **[src/game.ts](src/game.ts)** — Pure functional game state. `GameState` holds the puzzle, solution, `puzzleId` (content hash of the solution, from `hashSolution`), user board, given-cell mask, notes (bitmask per cell), notes mode, `started`/`paused`/timer fields, mistake count, and undo history (`Snapshot[]`). All state mutations return a new `GameState`. Entering a correct number auto-clears that digit from peers' notes. `createGame(difficulty, seed?)` — an optional `seed` reproduces a specific puzzle (daily puzzles); omitting it generates a fresh random one as before. The timer doesn't start until the first digit is entered (`started` flips inside `enterNumber`, value entries only); every state-mutating action no-ops while `paused`, so pausing holds even if a UI guard is missed. `pauseGame`/`resumeGame`/`togglePause` re-anchor `startTime` on resume so elapsed time excludes the paused interval.
- **[src/firebase.ts](src/firebase.ts)** — Initializes the Firebase app/auth/db from `VITE_FIREBASE_*` env vars, guarded against re-`initializeApp()`. `auth`/`db` are `Auth | undefined` / `Firestore | undefined` — initialization is wrapped in `try`/`catch` so a missing/invalid config (no env vars set, e.g. CI or a fresh checkout without `.env.local`) degrades to "stats disabled" instead of throwing and crashing every module that imports it, `main.ts` included.
- **[src/puzzleDoc.ts](src/puzzleDoc.ts)** — `boardToRows(board)` and `requireDb()`, plus `ensurePuzzleDoc(puzzleId, difficulty, puzzle, solutionHash, options?)` (creates `puzzles/{puzzleId}` on first sight, no-ops if it already exists; `options.isDaily`/`options.dailyDate` tag daily-puzzle docs). Shared by `recordPuzzleStart` and the daily-puzzle cache (`dailyPuzzle.ts`) so there's one doc-creation path, not two copies.
- **[src/stats.ts](src/stats.ts)** — `ensureAnonymousAuth()` (idempotent `signInAnonymously`, memoized as a module-level promise; rejects immediately if `auth` is undefined; does not cache a rejection, so a later call retries), `resetAnonymousAuthCache()` (clears that memoized promise — called by `signOutUser()` in `auth.ts` so the next call re-authenticates instead of reusing a now-stale user), `recordPuzzleStart(puzzleId, difficulty, puzzle, solutionHash)` (calls `ensurePuzzleDoc`, then increments `timesPlayed`), `recordPuzzleCompletion(puzzleId, elapsedMs)` (increments `completions`/`totalPlayTimeMs`), `recordUserPlay(puzzleId, difficulty, mistakes, elapsedMs)` (`setDoc`s `users/{uid}/plays/{puzzleId}` — overwrites, doesn't merge, so a repeat play of the same puzzle replaces its history entry rather than accumulating one), `fetchUserPlays()` (queries `users/{uid}/plays` ordered by `completedAt` descending). All throw via `requireDb()` if `db` is undefined. Failures are caught and logged in `main.ts`, never block gameplay.
- **[src/dailyPuzzle.ts](src/dailyPuzzle.ts)** — `seedFromString(str)` (single-pass FNV-1a → uint32), `todayUtc(now?)` (UTC `yyyy-mm-dd`), `dailySeed(date, difficulty)`, `dailyRandomDifficulty(date)` (deterministically picks from `DAILY_RANDOM_POOL` = easy/normal/hard, never expert), `generateDailyPuzzle(date, difficulty)` (calls `generatePuzzle(difficulty, dailySeed(...))` — fully local/deterministic, no Firestore read needed to play), `cacheDailyPuzzles(date)` (best-effort: checks `dailyPuzzles/{date}` existence *first* to short-circuit repeat clicks, then `ensurePuzzleDoc`s all four difficulties tagged `isDaily` and creates `dailyPuzzles/{date}` pointing at their ids + `random`; tolerates a `permission-denied` race from another client's concurrent create, since the value would be identical by construction), `MIN_CALENDAR_DATE` (`'2026-07-01'`, the earliest date the calendar view can browse to — the month daily-puzzle support itself shipped), and `dailyPuzzleId(date, difficulty)` (memoized `hashSolution(generateDailyPuzzle(...).solution)`, used by the calendar's completion scan — memoization matters since `'expert'` generation costs ~130ms per call).
- **[src/calendarView.ts](src/calendarView.ts)** — Pure, DOM/Firestore-free helpers for the calendar overlay, mirroring `statsView.ts`'s separation of pure logic from `main.ts`'s DOM wiring: `buildCalendarMonth(year, month, today, minDate, completedDates)` (always a 42-cell Sunday-start grid; a day's `status` is `'completed' | 'not-completed'` when selectable, `'unavailable'` otherwise — two-state only, since there's no "started but unfinished" doc for any date), `isDateSelectable`/`selectableDatesInMonth` (lexicographic `yyyy-mm-dd` range checks against `[minDate, today]`), `canGoToPreviousMonth`/`canGoToNextMonth`/`shiftMonth` (month-nav bounds), `formatMonthLabel`, `formatCalendarDayLabel(date)` (full accessible date label + "completed" suffix), and `difficultiesWithCompletions(plays)` (the set of difficulties a user has ever completed at all, used to skip expensive puzzle generation for difficulties with zero completions).
- **[src/auth.ts](src/auth.ts)** — `onAuthChange(callback)` (live `onAuthStateChanged` subscription for UI; no-ops instead of throwing if `auth` is undefined, since it runs unconditionally at boot rather than from a user action). `signInWithGoogle()` and `completeEmailLinkSignInIfPresent()` (the redirect-back half of `sendSignInLink(email)`) both **link** rather than replace when the current session is anonymous — `linkWithPopup`/`linkWithCredential` upgrade the existing anonymous uid in place, so play stats already written under it (via `stats.ts`) carry over into the real account instead of being orphaned. Both fall back to `signInWithCredential` on `auth/credential-already-in-use` (the same Google account/email is already tied to a different Firebase user, e.g. signed in on another device) — that fallback signs into the existing account rather than merging, abandoning the current anonymous session's stats; a deliberate, documented tradeoff, not a bug. `signOutUser()` calls `signOut` then `resetAnonymousAuthCache()`. `completeEmailLinkSignInIfPresent()` checks the URL shape (`looksLikeEmailSignInLink`, a Firebase-free heuristic) before requiring Firebase to be configured, so it doesn't warn on every plain page load. Email-link state persists in `localStorage` (not memory), since the flow completes on a fresh page load after the user clicks a link in their email client.
- **[src/persistedGame.ts](src/persistedGame.ts)** — `saveGame(state)`, `loadGame()`, `clearSavedGame()`. Serializes the in-progress `GameState` to a single `localStorage` key (`sudoku-saved-game`) so a backgrounded tab that the browser discards and reloads from scratch can resume instead of silently starting over. `difficulty` is read from `state.difficulty`, not a separate parameter (`state` can lag a synchronously-updated module variable during async generation). Versioned (`SCHEMA_VERSION`) and age-limited (24h) — a save that fails either check, or is unparseable, is discarded rather than rehydrated. Never persists (and clears any prior save for) a solved game; strips `history` (the undo stack, unbounded growth) before saving. All `localStorage` access is wrapped in `try`/`catch`, matching this repo's "never let storage/backend issues block gameplay" pattern from `firebase.ts`/`stats.ts`.
- **[src/statsView.ts](src/statsView.ts)** — Pure, DOM-free helpers for the stats/profile view: `summarizeByDifficulty(plays)` (per-difficulty completion count, best time, average time — `null` best/avg when a difficulty has zero completions; "completions" counts distinct puzzles solved, not total attempts, since a repeat play overwrites its history doc), `formatElapsed(ms)` (mm:ss), `formatDifficultyLabel(difficulty)` (capitalized). Kept separate from `src/stats.ts` (which does the Firestore I/O) so the aggregation math is unit-testable without mocking Firestore.
- **[src/main.ts](src/main.ts)** — DOM wiring. Builds the board and numpad on init, handles clicks and keyboard input (digits, Backspace/Delete/0 to erase, `N` for notes mode, `P` for pause/resume, arrow keys to navigate). Renders all cell classes (given, selected, peer, same-num, conflict, has-value, has-notes) and dims completed digits in the numpad. Shows a loading overlay during puzzle generation (yields to the browser with a 30ms timeout before the sync generation work) — `startNewGame()` guards overlapping calls with a module-level `gameGeneration` counter, since a slower stale call could otherwise overwrite a newer one's `state`. Calls `recordPuzzleStart` when a new game is created and `recordPuzzleCompletion`/`recordUserPlay` (once, guarded by a module-level flag) when the board is solved. `btnDaily`/`btnDailyRandom` start today's puzzle via a module-level `activeSeed` passed through to `createGame`; any regular difficulty pick, New Game, or Play Again clears it back to random generation. `render()` calls `saveGame` on every state change; `visibilitychange`/`pagehide` listeners save explicitly too, since the timer's per-second tick updates `state.elapsed` without going through `render()`. `init()` tries `tryRestoreGame()` before falling back to `startNewGame()` — a restored game that had already started comes back `paused` regardless of its saved pause state, so resuming after a surprise reload is always an explicit action. Sign-in UI: `#btnSignIn` opens `#signInOverlay` (Google popup or email-link form); `onAuthChange` drives `renderAuthState`, toggling `#btnSignIn`/`#signedInInfo`; `completeEmailLinkSignInIfPresent()` runs once at boot. `#btnStats` opens `#statsOverlay` (`openStatsOverlay()`/`closeStatsOverlay()` guarded by a `statsRequestId` counter against rapid re-clicks racing a stale fetch), independent of sign-in state (anonymous players see their own accrued history too). `#btnCalendar` opens `#calendarOverlay` (`computeCompletedDates` scans the visible month, cheapest-difficulty-first with early exit per day, guarded by `calendarRequestId`); `startDailyGame(targetDifficulty, date, dailyButton)` is shared by `#btnDaily`, `#btnDailyRandom`, and a calendar-day click alike. Mobile/short-viewport nav: `#secondaryNav` (daily buttons + stats + sign-in, grouped into one container so there's a single source of truth) becomes a slide-in drawer below `32.5rem` width **or** `50rem`/800px height (`openDrawer`/`closeDrawer`/`dismissDrawer` — the latter also restores focus to `#btnMenu`; `secondaryNav.inert` while closed and in drawer mode).

## Key design decisions

- **Notes as bitmask** — `notes[r][c]` is a 9-bit integer; bit `i` set means digit `i+1` is pencilled in. Toggle with XOR, clear with AND-NOT.
- **Hint cells become given** — `applyHint` marks the revealed cell as `given: true` so it becomes uneditable, matching standard Sudoku UI conventions.
- **Unique-solution guarantee** — `countSolutions(puzzle, 2)` is called after each removal during generation; cells are only removed when exactly one solution remains.
- **Undo does not re-increment mistakes** — snapshots capture `mistakes` at the time of the move, so undoing a wrong entry also restores the mistake count.
- **Solver tests cover `isValid` only** — `solve` and `countSolutions` are backtracking algorithms that are too slow to run against constrained boards in unit tests.
- **`getPeerCoords` deduplicates row/col/box** — box loop uses `r !== row && c !== col` to avoid duplicating cells already covered by the row and column sweeps (20 peers, not 24).
- **Yarn 4 standalone project** — an empty `yarn.lock` at the project root is required because `~/package.json` exists with a `packageManager` field; without it Yarn treats the project as a sub-workspace.
- **Puzzle ID = content hash of the solved grid, not a sequential counter** — generation is client-side and random, so there's no central sequencer; hashing the solution means two independently-generated identical puzzles collapse to the same Firestore doc/stats automatically.
- **`puzzle` is stored in Firestore as 9 row-strings, not a 9×9 nested array** — Firestore rejects nested arrays outright. `Board`'s `(number | null)[][]` shape is only ever a client-side/solver concept.
- **Daily puzzles are generated locally by every client, never fetched from Firestore to play** — `generateDailyPuzzle` is a pure function of `dailySeed(date, difficulty)`, so every browser independently computes the byte-identical puzzle; `dailyPuzzles/{date}` in Firestore is bookkeeping only, never a gameplay dependency.
- **Firestore/backend calls never block or fail gameplay** — every Firebase-touching call (`stats.ts`, `dailyPuzzle.ts`, `auth.ts`) is wrapped in `try`/`catch` or `.catch(console.warn)`; a write/read failure (offline, rules rejection, missing config) degrades silently rather than interrupting play. Same philosophy extends to `localStorage` access in `persistedGame.ts`.
- **`firestore.rules` isn't deployed via CLI** — it's pasted into the Firebase Console (Firestore Database → Rules → Publish) manually on every change; the file in this repo is the source of truth, verified live via scratch scripts (not committed) rather than a deploy pipeline.

## Testing notes

- **Playwright locators re-evaluate on every action** — e.g. `.cell:not(.given)` is live; once a hint reveals a cell it drops out of that locator. Snapshot `data-row`/`data-col` on the cell you're acting on, then re-locate by those attributes for follow-up assertions.
- **Wait for `#loading` to be hidden before reading board state** — puzzle generation is async (30ms yield + backtracking work); reading board state right after `page.goto()` or a difficulty click can race it.
- **Clue counts aren't asserted exactly in tests** — assert relative counts (expert < easy) rather than the exact 46/36/28/22 targets, since generation can stop removing early.
- **`vitest.config.ts` uses the `happy-dom` environment** (not `node`) — `auth.ts` needs `window.localStorage`/`location`/`prompt`/`history`, which don't exist under Node.
- **Firestore/live-backend changes are verified with scratch Playwright/Node scripts, not committed** — every `firestore.rules` change in this repo's history was confirmed against the real `sudoku-craigmcn` project this way (valid + rules-violating writes) before being considered done.

## Fonts & icons

- Outfit (via albertcss v0.18.0, `albert.min.css`) — delegated entirely to the CDN link, no font override in `styles.css`
- FontAwesome (sharp/light kit `87b0bcd87f`) for toolbar icons (undo, erase, pencil, lightbulb, checkmark). Icon glyphs may not render on a fully offline PWA reload even though static kit assets are cached (the kit's own runtime init needs something beyond that) — accepted as a cosmetic trade-off since every action button also carries a text label.

## PWA / offline support

`vite-pwa.config.ts` (shared by `vite.config.ts` and `vite.config.netlify.ts`) configures a Workbox `generateSW` service worker: precaches all built assets, plus `runtimeCaching` (CacheFirst) for the three external CDN origins this app depends on — albertcss, the Font Awesome kit's per-account webfont subdomain, and Google Fonts (pulled in transitively via albertcss's CSS `@import`). `scripts/copy-netlify-sw.mjs` copies the generated `sw.js`/`workbox-*.js` into the second Netlify build output directory (`netlify/sudoku/`), since the plugin only writes to the single resolved `build.outDir`. A page's first-ever load is never intercepted by its own installing service worker — offline support only kicks in from a second, SW-controlled load onward.
